# AWS 서울 이전 계획 (초안)

Railway 배포가 2026-11-10 미결제로 중단됐고, 사용자 결정은 **재결제 보류 · 실서비스 전
AWS 서울(`ap-northeast-2`) 이전**이다. 이 문서는 그 이전을 어떻게 할지에 대한 초안이다.

**이 문서로 돈이 나가거나 코드가 바뀌지는 않는다.** 비용은 전부 추정이고, 계정을 만들거나
리소스를 켜는 일은 사용자가 결정한 뒤에 한다.

> **비용 숫자는 전부 「추정」이다.** AWS 공개 가격표를 외워서 적은 값이라 실제와 다를 수
> 있고, 환율·프리티어·세금이 빠져 있다. **쓰기 전에 AWS 요금 계산기에서 확인할 것.**
> 이 문서에서 믿을 만한 것은 숫자 자체가 아니라 **옵션 간 상대적인 크기**다 — 특히
> "로드밸런서가 서버보다 비싸다"는 부분은 어느 해에 봐도 그렇다.

## 0단계 — 개인정보처리방침 §5 개정 (이전보다 먼저 또는 동시)

**서버를 옮기기 전에 처리해야 한다.** 방침 §5 수탁 표에 호스팅 업체가 이름으로 박혀 있다.

현재 문면:

```
| Railway Corp. (미국) | 서버·데이터베이스 호스팅 | 제1항의 모든 정보 | ... |
```

그리고 같은 절에 "국외 이전 항목: 위 표의 **미국·프랑스** 소재 업체에 기재된 항목이 해당
국가로 이전됩니다"가 있다.

바꿀 것 두 가지.

1. 수탁 표의 호스팅 행을 **AWS(한국)** 로 교체
2. **국외 이전 문구에서 호스팅을 제외** — 서울 리전은 국내다. 남는 국외 이전은
   Anthropic(미국), Expo·Google FCM(미국), Brevo(프랑스)뿐이다

**방침 본문 개정은 supervisor 몫이다.** BE 는 사실관계만 제공하고 문안을 쓰지 않는다.

시행 시점은 **이전 전 또는 이전과 동시**여야 한다. 서버를 먼저 옮기면 그 사이 방침이
사실과 다른 상태가 되고, 그건 방침 위반이 아니라 "방침이 거짓인 기간"이다.

고지 방식은 **국외 → 국내 이동이라 이용자에게 불리하지 않은 개정**으로 보여, 방침 자체의
규칙("불리하지 않은 개정은 시행일 고지")이 적용될 여지가 있다. 다만 이건 법률 판단이므로
**변호사 검토 항목에 병기**해 두고, 확정 전에는 7일 고지를 기본으로 잡는 편이 안전하다.

## ① 후보 구성 비교

세 안 모두 **단일 인스턴스**를 전제로 썼다. 이유는 ⑤에 적었다 — 지금 코드는 인스턴스를
늘리면 로그인이 깨진다.

### (a) Lightsail 컨테이너 + Lightsail PostgreSQL

| | |
|---|---|
| 월 비용 (추정) | 컨테이너 micro 약 $10 + DB micro 약 $15 = **$25, 약 3.5만 원** |
| 운영 난이도 | **가장 낮다.** 컨테이너 이미지를 올리면 HTTPS·도메인·헬스체크가 딸려 온다 |
| 백업·복구 | DB 자동 스냅샷 제공. 복구는 콘솔에서 스냅샷 → 새 인스턴스 |
| 확장성 | 낮다. 수직 확장(요금제 변경)만 현실적이고, 그 이상 가면 (c)로 옮겨야 한다 |

Railway 와 성격이 가장 비슷하다. TLS 인증서를 Lightsail 이 관리하므로 certbot 갱신을
걱정할 일이 없다.

### (b) EC2 1대 + docker compose (BE + nginx + PostgreSQL 볼륨)

| | |
|---|---|
| 월 비용 (추정) | t4g.small 약 $15 + EBS 30GB 약 $3 + 탄력적 IP(연결 시 무료) = **약 $18, 2.5만 원** |
| 운영 난이도 | **가장 높다.** OS 패치, PostgreSQL 업그레이드, 백업 스크립트, TLS 갱신이 전부 사람 몫 |
| 백업·복구 | 직접 만들어야 한다. `pg_dump` 크론 + S3 업로드, EBS 스냅샷. **검증까지 직접** |
| 확장성 | 수직 확장만. DB 가 같은 호스트라 분리 작업이 나중에 한 번 더 생긴다 |

가장 싸고 가장 자유롭다. 그 대가로 **DB 를 같은 서버에 두는 선택**이 붙는데, 운영자가
1인이면 백업 검증까지 챙기기 어렵다. 데이터를 잃는 사고는 비용 차액으로 못 메운다.

웹(FE 정적 번들)을 같은 nginx 로 서빙할 수 있어 그 점은 이득이다.

### (c) ECS Fargate + RDS

| | |
|---|---|
| 월 비용 (추정) | Fargate 0.25vCPU/0.5GB 약 $9 + **ALB 약 $20** + RDS db.t4g.micro 약 $13 + 스토리지 약 $3 = **약 $45, 6.3만 원** |
| 운영 난이도 | 중간. 관리형이라 손은 덜 가지만 **처음 세팅할 개념이 많다**(태스크 정의, 서비스, 타깃 그룹, 보안 그룹, VPC) |
| 백업·복구 | RDS 자동 백업·PITR. 세 안 중 가장 든든하다 |
| 확장성 | 가장 좋다. 다만 **지금 코드로는 태스크를 2개로 못 늘린다**(⑤ 참고) |

**ALB 가 서버보다 비싸다.** 지금 규모에서 ALB 가 주는 것은 TLS 종료와 헬스체크인데,
(a)는 그 둘을 요금 안에 포함해서 준다.

## ② 추천 — (a) Lightsail

초기 사용자 수백 명, 운영자 1인이라는 조건에서는 (a)가 맞다.

  원은 싸다. 특히 DB 백업은 "만들어 두었다"가 아니라 "복구해 봤다"여야 쓸 수 있는데,
  그 검증까지 직접 할 여력이 없다면 관리형 DB 가 답이다
- **(c)는 지금 필요하지 않은 것에 돈을 낸다.** ALB·VPC·타깃 그룹은 인스턴스를 여러 개
  굴릴 때 값어치가 생기는데, 지금 코드는 인스턴스를 늘릴 수 없다(⑤). 늘릴 수 있게
  고친 다음에 (c)로 가는 순서가 맞다
- Railway 와 운영 모양이 가장 비슷해서 **이전 자체의 위험이 가장 작다.** 컨테이너
  이미지를 올리고 환경변수를 넣는 방식이 그대로다

(b)를 고를 만한 경우는 하나다 — **FE 웹까지 같은 서버에서 서빙하고 싶고**, 백업 운영을
감당할 생각이 있을 때. 그때는 ⑤의 nginx 설정을 반드시 같이 볼 것.

## ③ 절차

### 0. 방침 §5 개정 (위 0단계)

### 1. 계정·리전

- 리전은 **`ap-northeast-2`(서울)** 로 고정. 다른 리전에 리소스를 만들면 국외 이전이
  되살아나 방침을 다시 고쳐야 한다
- 루트 계정에 MFA, 작업용 IAM 사용자 별도 생성. 루트로 일상 작업하지 않는다
- 예산 알림(Budgets)을 **먼저** 만든다. 미결제로 한 번 중단된 전력이 있다

### 2. 도메인·HTTPS

- 도메인을 하나 정한다. **옛 Railway 주소(`kickoffbe-production-7275.up.railway.app`)는
  카카오·네이버 콘솔과 FE 소스에 박혀 있으므로**, 새 도메인이 정해지는 순간 ④의 목록이
  전부 작업 대상이 된다
- (a) Lightsail: 컨테이너 서비스가 `*.<region>.cs.amazonlightsail.com` 을 주고, 커스텀
  도메인은 Lightsail 인증서로 붙인다
- (b) EC2: Caddy 를 권한다. certbot 보다 설정이 짧고 갱신이 기본이다. nginx + certbot 도
  되지만 갱신 실패를 알아차릴 장치를 따로 둬야 한다
- (c) ALB: ACM 인증서(무료) + ALB 리스너

### 3. DB

- **PostgreSQL 16 이상**으로 만든다. Railway 가 16 이었고 테스트도 `postgres:16` 으로
  돈다
- 스키마는 **Flyway 가 만든다.** 빈 DB 에 `DB_URL`·`DB_USERNAME`·`DB_PASSWORD` 만 주고
  앱을 띄우면 V1~V21 이 순서대로 적용된다. 손으로 DDL 을 넣지 말 것
- **옛 데이터 이전은 선택이다.** 지금 Railway DB 에 실사용자 데이터가 있는지는 별도
  확인이 필요하다. 없다면 빈 DB 로 시작하는 쪽이 깨끗하다. 있다면 Railway 를 한 번
  되살려 `pg_dump` → `pg_restore` 해야 하는데, **Flyway 이력 표(`flyway_schema_history`)
  까지 함께 옮겨야** 앱이 재적용을 시도하지 않는다
- **DB 콜레이션은 기본값(`en_US.utf8`)이어도 된다.** 한글 정렬이 그 콜레이션에서 가나다순이
  아니지만, 정렬이 필요한 두 쿼리는 `sortkey()` 로 `COLLATE "C"` 를 못박아 두었다
  (`SortKeyFunctionContributor`). **콜레이션을 "고치려" 하지 말 것** — 2026-09-28 에
  이것 때문에 운영에서만 구장 목록 순서가 엉킨 사고가 있었고, 지금 구조는 DB 설정과
  무관하게 같은 순서를 낸다

### 4. 환경변수 투입

**[README 의 재배포 체크리스트 ①](../README.md#-환경변수-전수)** 이 전수 목록이다(32개).
여기서 되풀이하지 않는다 — 두 곳에 적으면 한쪽만 낡는다.

이전 특유의 주의만 적는다.

- `SPRING_PROFILES_ACTIVE` 는 `Dockerfile` 에 `prod` 가 박혀 있다. **이미지를 그대로
  쓰면 따로 줄 필요가 없다.** 직접 `java -jar` 로 띄울 때만 줘야 한다
- `PORT` 는 Lightsail 컨테이너가 주입하지 않는다 — 컨테이너 설정에서 포트를 8080 으로
  열어 주거나 `PORT` 를 명시한다
- `OAUTH_CALLBACK_BASE_URL` 을 **새 도메인으로 명시하는 편이 안전하다.** 비우면 요청
  오리진에서 만드는데, 프록시가 `X-Forwarded-Proto` 를 안 넘기면 `http://` 로 만들어져
  제공자가 거부한다
- `CORS_ALLOWED_ORIGINS` 는 FE 웹 도메인이 정해진 뒤에 좁힌다. 지금 비워 두면 전부 허용
  (현행 유지)

### 5. 배포 자동화 (최소안)

지금은 `main` 푸시 → Railway 자동 재배포였다. 그 편의를 잃지 않는 최소 구성이다.

```
GitHub Actions (main 푸시)
  → ./gradlew test            # 통과해야 다음으로
  → docker build              # 저장소의 Dockerfile 그대로
  → ECR 푸시
  → (a) Lightsail: aws lightsail create-container-service-deployment
    (b) EC2:       ssh + docker compose pull && up -d
    (c) ECS:       aws ecs update-service --force-new-deployment
```

- **테스트를 CI 에서 돌린다.** `Dockerfile` 은 `-x test` 로 빌드한다(주석에 이유가 있다 —
  배포마다 632개를 다시 도는 값이 크다). 그래서 CI 가 그 자리를 메워야 한다. 지금은
  로컬에서만 돌고 있어 **이게 비어 있는 칸이다**
- 마이그레이션이 있는 커밋은 `postgresTest` 까지 돌려야 한다(`postgres:16` debian 이미지 —
  alpine 으로 되돌리지 말 것, README 테스트 절 참고)
- AWS 자격증명은 GitHub OIDC 로 받는 편이 좋다. 장기 액세스 키를 리포지토리 시크릿에
  넣지 않는다

### 6. 롤백

- **(a) Lightsail**: 이전 배포 버전이 콘솔에 남아 그걸로 되돌린다. 가장 간단하다
- **(b) EC2**: 이미지 태그를 커밋 해시로 달고 `docker compose` 의 태그를 되돌린다.
  `latest` 만 쓰면 되돌릴 대상이 없어진다
- **(c) ECS**: 이전 태스크 정의 리비전으로 서비스 업데이트
- **DB 마이그레이션은 롤백되지 않는다.** Flyway 에 되돌리기가 없다. 스키마를 바꾼
  배포를 되돌려야 하면 **앞으로 가는 마이그레이션(V22)을 새로 써야** 한다. 유일한 예외는
  마이그레이션이 *실패*한 경우다 — PostgreSQL 은 DDL 이 트랜잭션이라 실패하면 이력도
  남지 않고 통째로 되돌아간다(V18 때 확인했다)

## ④ 재배포 체크리스트와의 연결

이전 당일에 볼 것은 이 문서가 아니라 **[README 의 재배포 체크리스트](../README.md#재배포-체크리스트)**
다. 이 문서는 "어디로 어떻게 갈지"를 정하는 용도이고, 체크리스트는 "가는 날 빠뜨리지
않을 것"을 모은 것이다.

연결되는 지점 셋.

- **① 환경변수 전수** — 32개. 기동이 막히는 것은 `DB_*` 세 개뿐이고 나머지는 조용히
  기능만 죽는다. "뜨면 성공"이 아니다
- **② 도메인 변경** — 새 도메인이 정해지면 카카오 콘솔 3곳(Redirect URI·사이트 도메인·
  맵 referer), 네이버 콜백, FE 소스 3자리(`main` 에서 한 번, `kickoff_fe_preview` 는
  스냅샷이라 따로 다시 묶어야 한다)
- **③ 키 재발급** — 2026-09-07 에 Railway 환경변수 전체가 대화창에 붙여졌다. 확정 재발급
  8개가 있고 **이전과 함께 처리하는 것이 가장 싸다** — 어차피 새 환경에 값을 새로 넣는
  작업이라, 그때 새 값을 넣으면 한 번에 끝난다

## ⑤ 코드 전제 — 옮기기 전에 알아야 하는 것

이전 자체보다 여기서 사고가 난다. 전부 코드를 읽어 확인한 것이다.

### 인스턴스를 늘리면 로그인이 깨진다 (가장 중요)

상태를 들고 있는 네 곳이 **전부 인메모리 `ConcurrentHashMap`** 이다.

| 클래스 | 들고 있는 것 | 인스턴스가 둘이면 |
|---|---|---|
| `OAuthStateStore` | 소셜 로그인 CSRF state | A 에서 시작한 로그인이 B 로 콜백되면 **state 불일치로 실패** |
| `OAuthExchangeCodeStore` | 웹 OAuth 일회용 코드(60초) | A 가 발급한 코드를 B 가 모른다 → **교환 실패** |
| `LoginAttemptLimiter` | 로그인 실패 횟수 | 한도가 인스턴스마다 따로 세어져 **실질 한도가 2배** |
| `SmsDispatchQuota` | 문자 발송 한도 | 같은 이유로 **문자 한도가 2배** — 실제 비용이 나간다 |

그래서 **지금 코드는 단일 인스턴스 전제다.** 인스턴스를 늘리려면 이 네 곳을 공유 저장소
(Redis 등)로 옮기거나 스티키 세션을 붙여야 하고, 둘 다 이 이전의 범위가 아니다.
구성 비교에서 (c)의 확장성을 깎은 이유가 이것이다.

### `X-Forwarded-For` 를 넘기지 않으면 한도가 한 사람 것처럼 묶인다

`ClientIp.of()` 는 `X-Forwarded-For` 의 **첫 값**을 쓰고, 없으면 `remoteAddr` 로 떨어진다.
프록시 뒤에서 이 헤더가 없으면 **모든 요청이 프록시 IP 하나로 보인다** — 로그인 실패
한도와 문자 발송 한도가 전부 같은 키에 묶여서, 한 사람이 한도를 쓰면 나머지가 막힌다.

- ALB·Lightsail 로드밸런서는 자동으로 붙인다
- **(b) nginx 는 직접 설정해야 한다**:
  ```nginx
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
  proxy_set_header X-Forwarded-Host $host;
  ```

### `X-Forwarded-Proto` 가 없으면 소셜 로그인 콜백이 `http://` 로 나간다

prod 프로파일에 `server.forward-headers-strategy: framework` 가 있어, 스프링이
`X-Forwarded-Proto`·`Host` 를 보고 요청 주소를 바로잡는다. 그 헤더가 없으면 콜백 URI 가
내부 주소·`http` 로 만들어져 **제공자가 거부한다.** 안전망은 `OAUTH_CALLBACK_BASE_URL`
을 명시하는 것이다.

### 헬스체크로 쓸 경로

**액추에이터가 없다**(`spring-boot-actuator` 의존성 없음). `/actuator/health` 는 존재하지
않으므로 로드밸런서 헬스체크를 실제 경로로 잡아야 한다.

- **`GET /api/auth/signup-policy`** 가 적당하다 — 인증 불필요, 200, 설정값만 읽어
  DB 를 건드리지 않는다(= 가볍다)
- 다만 그래서 **DB 가 죽어도 200 이 나온다.** DB 까지 보려면 `GET /api/stadiums?size=1`
  을 쓰되, 헬스체크 주기마다 쿼리가 나간다는 점을 감수할 것
- **없는 경로를 헬스체크로 쓰지 말 것.** 토큰 없이 부르면 404 가 아니라 **401** 이다
  (`anyRequest().authenticated()` 가 라우팅보다 먼저 걸린다)

### 시간대·인코딩은 이미 고정돼 있다

- `BeApplication` 정적 초기화에서 `TimeZone.setDefault("Asia/Seoul")` 을 한다. **컨테이너
  TZ 를 맞출 필요가 없다.** 스케줄 크론도 `zone = "Asia/Seoul"` 로 각각 박혀 있다
- `Dockerfile` ENTRYPOINT 에 `-Dfile.encoding=UTF-8` 이 있다. 베이스 이미지를 바꾸더라도
  한글이 깨지지 않는다. **이 플래그를 지우지 말 것**

### 스케줄 작업이 인스턴스마다 돈다

`@Scheduled` 는 인스턴스별로 실행된다.

- `RetentionCleanupJob`(04:30 KST) — 삭제가 멱등이라 여러 번 돌아도 안전하다(주석에 그
  판단이 적혀 있다)
- `StadiumSyncScheduler`(05:00 KST) — **멱등하지 않다.** 공공 API 응답에 없는 행을
  삭제하고 새 행을 넣는 작업이라, 두 인스턴스가 동시에 돌면 경쟁한다. 단일 인스턴스면
  문제가 없다

### 그 밖에 확인할 것

- **`local.yaml` 을 이미지·서버에 올리지 말 것.** 환경변수를 이긴다. `.dockerignore`
  첫 줄에서 빼고 있다
- **`/h2-console` 은 조치 완료다.** 확인해 보니 운영에서 콘솔이 떠 있던 것은 아니었다 —
  `spring.h2.console.enabled` 가 dev 블록에만 `true` 라 서블릿이 등록되지 않는다. 다만
  막고 있는 것이 프로퍼티 한 줄뿐이고 **H2·h2console 모듈은 운영 이미지에 그대로
  들어간다**(`BOOT-INF/lib` 에서 확인). 그래서 시큐리티 규칙을 dev 에서만 `permitAll`,
  그 밖에서는 `denyAll` 로 갈랐고 `H2ConsoleAccessTest` 가 그 경계를 지킨다.
  이전 후 프로브에서도 한 번 볼 것 — 토큰을 주고 불러 **403** 이면 맞고, 404 면 규칙이
  빠진 것이다(= 토큰만 있으면 닿는 상태)
- **`server.shutdown: graceful` 을 명시했다.** 전에는 버전 기본값에 기대고 있었다. 롤링
  배포에서 즉시 종료면 그 순간 처리 중이던 요청이 그냥 끊긴다
- `docs/terms-of-service.md`·`docs/privacy-policy.md` 는 **이미지 빌드에 들어간다**
  (`Dockerfile` 이 `COPY docs docs`). `.dockerignore` 가 `docs` 를 빼면서 이 두 장만
  예외로 들여보내는 구조라, 둘 중 하나가 어긋나면 빌드는 성공하고 운영에서만
  `/terms`·`/privacy` 가 500 이 난다
